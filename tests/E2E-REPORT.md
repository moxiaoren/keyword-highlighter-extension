### K17 · 颜色字段改胶囊 / 复用底色缩短 / 图片尺寸一行 —— **已优化（用户实测）**
- **用户原话**：①「基本信息模块的高亮颜色，底色、文字颜色放在框里面，不要单独列一行，减少占用空间。
  参考匹配规则三个胶囊」；②「重要笔记模块的复用高亮底色，改成复用底色，减少长度」；
  ③「图片尺寸从两行改成一行 `图片尺寸(px)：输入框`」。
- **① 颜色改胶囊**：`ColorField` 新增 `chip` 模式 —— 色点显示当前颜色，**未设色为虚线空心圈＝继承**
  （继承链 `分组色 > 全局默认色` 写在 tooltip 里），标签简称「底色」。
  旧形态是"标签一行 + 色块一行"（两行 92px），现在两个胶囊并排一行（26px）。
  关键实现点：胶囊模式下**不能**复用原来那套 `swatch.textContent = value || '继承'` ——
  会把胶囊里的色点与标签一起抹掉，所以 `sync()` 按模式分支。
- **② 「复用高亮底色」→「复用底色」**（长度减半）。
- **③ 图片尺寸一行**：`FieldMap` 新增 `inline: true`（标签与控件同一行，冒号由 CSS `::after` 补，
  这样非 inline 模式不会多出一个多余的冒号）；占位文案同步缩短为「留空＝默认」以免被截断。
- **结果**：**弹窗 429 → 422px**（自最初 753px 起累计 **−331px / −44%**）。
  现在限制高度的是「单元格组合 + 抓取后续字段」与「重要笔记」两列（约 292px），基本信息已经更矮。
- **回归网**：真浏览器断言更新 —— 两个颜色胶囊必须带色点、文案为「底色 / 文字颜色」、同一行且宽度 ≤120px；
  「复用底色」文案；图片尺寸标签与输入框同一行且容器高度 ≤34px。

### K18 · 两处位置调整 + 尺寸标签过长挤压输入框 —— **已优化（用户实测）**
- **用户原话**：「位置要如图换一下：基本信息模块的底色、文字颜色胶囊放在**匹配规则三个胶囊下面**；
  复用底色胶囊和图片大小输入框放在**重要胶囊的后面（一行展示）**。注意，图片大小前面的文本不用这么长，
  挤压太多输入框位置」。
- **① 颜色胶囊上移**：`bgColor` / `textColor` 在字段表中的位置提到三个匹配开关之后 ——
  它们同属"胶囊"，落在同一个胶囊行容器里；容器 245px 装不下 5 个时自动折第二行，
  实测分行正是 `[正则 大小写 全词]` / `[底色 文字颜色]`（e2e 直接断言这两行）。
- **② 重要 / 复用底色 / 尺寸同一行**：把 `impNoteUseHlColor` / `imgSize` 提到 `important` 之后。
  `复用底色` 与「重要」都是胶囊 → 自动同一行；`尺寸` 是 inline 字段，
  为此把 `.kh-fld-inline` 的 `flex-basis` 设为 **60px**（而不是半行宽），
  这样它能与胶囊行**挤在同一行**，剩余宽度再给输入框（`flex-grow: 1`）；
  同时把胶囊行的 `flex-grow` 从 1 改成 0，免得它把剩余宽度全吃掉、把输入框压没。
- **③ 尺寸标签缩短**：「图片尺寸(px)」→「尺寸」（原标题 78px，在 87px 的字段里输入框只剩 ~45px）；
  占位文案「留空＝用全局默认」→「默认」，完整说明移入 `title` tooltip。
- **踩到的坑**：改字段顺序时**插入了新的 `bgColor`/`textColor` 却忘了删旧的**，
  于是这两个颜色控件被渲染了两遍（量几何时同一行出现两次才发现）。
  —— 这正是"字段表是单一来源"之外的另一件事：**顺序也是数据**，改顺序要移动而不是复制。
- **回归网**：e2e 断言升级为"胶囊必须恰好分两行且第二行就是 `底色/文字颜色`"、
  「重要 / 复用底色 / 尺寸」三点 y 坐标差 <8px、尺寸标签为「尺寸」且输入框宽度 ≥40px。

### K19 · 三列高度不齐 / 备注框默认出滚动条 / 底色再缩短 —— **已优化（用户实测）**
- **用户原话**：①「三列的高度不齐，不太美观。统一一下」；②「适当增加这个弹窗总高度，
  让备注输入框不会默认就要滚动条（如图框起来部分）」；③「重要笔记里的复用底色胶囊改成底色吧，
  给后面的图片尺寸留出空间」。
- **先量再改**：
  - 三列底边实测 `564 / 596 / 551`（相差 45px）；
  - 备注框实测 `clientHeight 52 / scrollHeight 93` —— 空框时占位文案有 4 行，**溢出 41px**，所以一打开就有滚动条。
- **① 三列齐平**：`.kh-editor-cols` 的 `align-items` 从 `flex-start` 改为 `stretch`（flex 默认），
  并让**列内最后一张卡片 `flex: 1 1 auto`** —— 只拉伸列而不拉伸卡片是没用的（列本身没有边框/背景，
  看到的是卡片的边框）。改后实测三列均为 301px、底边 600 全等。
- **② 备注框高度**：`rows` 2 → 4（正好 93px ≈ 占位文案高度）。改后 `scrollHeight == clientHeight`，
  无滚动条。这是本轮唯一**主动增加**的高度（弹窗 422 → 431px），用户明确要求"适当增加总高度"。
- **③ 「复用底色」→「底色」**：给同行右侧的「尺寸」输入框让出宽度；完整含义
  （"复用关键词高亮底色（重要笔记卡片背景）"）写进胶囊 tooltip。
- **回归网**：e2e 新增断言"三列底边差 ≤2px"、"备注框 `scrollHeight <= clientHeight + 1`（默认无滚动条）"，
  并把「复用底色」的断言改为「底色」。

### K20 · 胶囊去掉勾选框（只用颜色区分开关） —— **已优化（用户实测）**
- **用户原话**：「关键词编辑界面的胶囊取消前面的勾选框吧，以胶囊颜色做区分。如图，启用是勾选状态，
  启用组合是未勾选状态」。
- **做法**：选中＝品牌色底 + 品牌色边框 + 品牌色加粗文字；未选中＝白底 + 常规边框
  （实测 `rgb(234,241,251)` vs `rgb(255,255,255)`）。`<input type="checkbox">` **仍留在 DOM 里**
  （labelable、可聚焦、可按 `#fld-<key>` 定位），只是视觉隐藏（`position:absolute; 1px; opacity:0`），
  键盘用户另有 `:focus-within` 焦点环 —— 自动化断言、键盘操作、保存往返全不受影响。
- **顺带抓到一个真问题**：去掉勾选框后每个胶囊窄了约 17px，

>  反之亦然。如果确实因为某些原因无法一致，请告知我原因让我决策。"

- **审计结论（改之前）**：两个真实的结构性分叉
  1. `combo.js` 自己有一份 `matchIn()`（逐文本节点跑正则），核心词/标题词都走它 —— 而普通词走的是
     内核的 `node-regex`（单节点）+ `inline-run-regex`（跨节点 run）。于是**跨节点能力只有一边有**
     （K45 修的"组合词命不中被拆开的词"就是这么来的），且未来任何匹配语义调整都要改两处。
  2. `combo/cells.js` 自己抄了一份"哪些文本可扫描"的过滤器（`SKIP_TAGS` / `isContentEditable` / 插件 UI），
     与内核 `collectTextNodes` 各写一遍 —— 只要有一处走偏，"组合词能扫到的文本"就与普通词不一致。
- **改法（把"两边"变成"一份 + 一个范围参数"）**：
  - 内核新增 `Scanner.util.matchKeyword(nodes, pattern, ctx, {flags, within, matchOne})` ——
    **唯一的关键词匹配入口**，产出 `{single, cross}`（单节点命中 + 真跨节点命中，不重复计数）。
    `matchIn()`（单节点匹配，含全词跨节点守卫 / `g` 兜底 / 空匹配保护）也从 `combo.js` **搬进内核**。
  - 四个调用点全部收敛到它：`node-regex`（普通词·整页）、`inline-run-regex`（普通词·跨节点）、
    组合词核心词（`within: 定位到的格子`）、组合词标题词（同）。
  - **组合词与普通词的差别现在只剩 `within`**：`combo.js` 里已经没有 `new RegExp`、没有自建遍历、
    `KH.Combo.matchIn` 这个"第二份实现的入口"也已删除（留着就是后门）。
  - `Cells.textNodesIn()` 改为委托内核 `Scanner.util.textNodesIn`，本文件不再有任何"可扫描文本"判据。
- **防复发（一正一反两道）**：
  - **静态红线**（meta-check 新增第 46 项「匹配口径单源」，从 45 → 46 项）：
    组合词文件里出现自建正则 / 自建 exec 遍历，或 `cells.js` 里出现 `createTreeWalker` /
    没委托内核 `textNodesIn` → **出包直接红灯**。
    反向验证：往 `combo.js` 塞一个 `new RegExp('x')` → 红；往 `cells.js` 塞一个 `createTextWalker` → 红。
  - **行为红线**：`tests/specs/match-parity.test.js`（14 条）用**同一批装置把同一个词跑两遍** ——

    是否跨节点 / 分段数 / 命中条数。12 条匹配矩阵（单节点、拆两段、拆三段、夹空 span、
    一格两次、大小写开关、正则多分支、全词正反例、跨节点+全词、块级隔开反例）

  4. **内容脚本不可达时落回弹窗内联**（chrome://、扩展页、内容脚本被禁）→ 保底永远能加词。
- **配套改动**：`manifest.content_scripts` 增加 `src/platform/storage.js` + `src/ui/{fieldmap,components/*}`（**无需新权限**）

- **回归网**：e2e 内容层新增「消息直达当前页 → Shadow DOM 里的 lg 三列编辑器」——

### K31 · 实现「跨文本节点命中」（用户拍板：拆开的词也要命中，且各段保留自己的颜色） —— **已实现**

  1. 用现成的 `carrier()` 把**相邻行内文本节点**串成 run（块级边界断开）；

### K30 · 深入场景核查：被拆开的词 / 全词边界 / 部分着色 + 悬浮备注 —— **已核查（含一处待决策）**

- **【结论 1：跨节点确实不命中，这是 1.52 继承下来的既定口径，不是本次回归】**
  `scanner.js` 顶部早就写着：「旧版 v1.10.x~v1.52.0 的匹配始终在**单个文本节点内**完成，

- **【结论 2：用户描述的"命中 + 其中一部分是红色"在当前实现里是矛盾组合】**

- **【待决策：要不要做"跨节点命中"】**（本次只核查，未实现）

### K29 · 默认文字色不再覆盖网页自身的文字色（红字被刷成黑字） —— **已新增（用户场景）**
- **用户原话**：「关于默认文字颜色我有个场景。就是原本网页有标红的内容，被命中之后，红字变成了黑色。
  这种情况可以解决么，保留原来网页的字体颜色（除非原字体颜色配合高亮的底色会导致文字不显）」。
  「底色默认还是维持现状，即便原网页有底色也覆盖。」
- **根因**：`renderer._ensureGroupStyle` 里**无条件**拼 `color:` —— 无论用户有没有设过文字色，
  命中后都把网页自身的颜色刷掉。
- **改法：三档**
  1. **默认文字色 → 规则里不写 `color`**（组名加 `-auto` 后缀），网页自身的颜色原样保留；
  2. **原色与底色分不开时 → 兜底档**（组名 `-fix`），写一个看得清的颜色
     （优先用配置的默认文字色，它自己也分不开时按底色明度取黑/白）；
  3. **关键词/分组显式设过的文字色 → 照旧强制**（那是用户明确的选择）。
  实现要点：`resolveVisual` 增返 `textIsDefault`（哪个来源的文字色），渲染层按 Range 决定落到哪一档；
  每个 Range 需要读一次元素计算色，按元素缓存（一次 render 一份），避免大量命中时重复取样式。
- **★ 判据只用色差 ΔE，不用亮度对比度 —— 这是算出来的，不是拍的**：

  |---|---|---|---|

  | 橙 `#ff9500`（同色） | 1.00 | 0 | 兜底 |
  | 近似橙 `#ffa733` | 1.13 | 12 | 兜底 |
  | 深橙褐 `#c76b00` | 1.73 | 22 | 兜底 |
  | 白 `#ffffff` | 2.20 | 88 | 保留（亮暗接近但颜色分得开） |
  | 黑 `#000000` | 9.55 | 110 | 保留（最常见，不能误伤） |

#### ② 拖到边界冒出卡片：**v2 换成坐标判据后引入的回归**
- **真浏览器复现（`_e2e/repro-drag.js`）**，事件流说得很清楚：
  ```
  pointerdown @661,42  → DIV      ← 面板标题栏（插件自身 UI）
  pointerup   @995,109 → HTML     ← 页面边界处
  click       @995,109 → HTML     ← 浏览器把 click 派发到两者的**共同祖先**
  松开后：卡片 hidden=false，正文 =「审核不通过📋×这是备注：状态词的解释。」
  ```
- **机制**：浏览器对一次交互派发的 `click`，其 target 是 `pointerdown` 与 `pointerup` 两个目标的
  **共同包含祖先**。拖动面板时 down 在面板里、up 在页面内容上 → `click` 落在 `<html>`/`<body>`，
  而坐标是松手处。v2 的高亮是纯 CSS Highlight（无 DOM 节点），命中判定只能**按坐标**（`hitAtPoint`），
  于是这次"补发的 click"被当成了命中点击 → 在松手处弹出固定备注卡片。
- **为什么偏偏是"拖到边界"**：边界处 caret/几何回退容易解析到邻近的命中词，于是松手点"看起来"命中了。

- **修复**：`note-card.js` 里记下最近一次 `pointerdown` 的来源；`click` 时若**不是从页面内容按下**的

- **已验证没有误伤**（双向断言，都进 e2e）：

### K11 · 空值口径两套规则（`-` 算空、`无` 算内容）—— **已统一**
- **用户实测提问**："如果右格是 `-` 加上一个按钮，这个 `-` 会被识别为空么。因为有时会用 `-` 占位当作空"
- **答案：会** —— 按钮先被剔除，剩下的 `-` 没有字母数字，判空。但顺着这个问题查出**同一概念两套规则**：
  - 触发判据（`triggerOk`）只问"有没有字母数字" → `-` 算空，`无` / `暂无` / `N/A` 却算**内容**；
  - 「下一字段」判据用的是 `isPlaceholderText`（纯符号占位集）→ `-` 算空。
  同一个"这格有没有内容"，两处口径不一致，正是这类语义 bug 的温床。
- **修复**：统一为**唯一口径** `isPlaceholderText`，触发判据（含假表格分支）显式过一遍它；
  词表从"纯符号"扩到符号 + 文字占位：`无` / `暂无` / `没有` / `无数据` / `暂无数据` / `未填写` / `未设置` / `未配置` /
  `N/A` / `null` / `none` / `undefined` / `nil`，**全串锚定**（`^…$`）—— `无理由退货`、`N/A 待补` 这类真值不会被误判。
  词表是白名单：漏收只会**多显示一条**，不会丢内容。
- **实测（`_e2e/probe-placeholder.js`，15 种组合）**：`-` / `——` / `~` / `/` / `--` / `无` / `暂无` / `N/A` 后面挂按钮
  一律判空；`- 备注：需补材料` 判有内容；**0 处不符**。
- **注意区分（装置实测）**：占位串作为**字段值**仍会照常出现在抓取块里 —— 例如「包名」这一列的某行值是 `-`，
  面板里就显示一行 `-`。这是**值**、不是**触发**：抓取块要按行对齐（多列块丢行会串位），所以不动它。
- **回归网**：`meta-check` 的控件契约红线扩到 6 条（新增"必须共用 `isPlaceholderText`"与"必须有文字占位词表"）；
  单测新增 **13 条**（占位口径正反例 + 11 种"占位串 ± 控件"）；真浏览器断言改为按**值行数**判定
  （3 个"只有控件"的行不该产生值行），比原先"某行标签名有没有出现"实在得多。

### K10 · 仅抓取触发判据把「控件/按钮」也算成了内容 —— **已加固**
- **用户口径**：核心关键词留空的「仅抓取」模式下，判断标题词（左格）对应的右格是否为空时，
  **右格里的控件 / 按钮不应纳入判断**。
- **实测（探针 `_e2e/probe-trigger.js`，用交付仓库自己的垫片跑真实代码）**：
  22 种真实后台形态里 **10 种仍会被当成"有内容"**：
  `<span class="opt-col">编辑</span>`、`<div class="operate">`、`<span class="caozuo">`、`<div class="cell-ops">`、
  `<a class="edit">`、`<span class="edit">`、`<a class="el-link" href="javascript:;">`、`<span style="cursor:pointer">`、
  `<div class="opt-desc">`、`<a href="javascript:void(0)">`。
- **根因（三条）**：
  1. `<a>` 与非 `<a>` **两套类名判据漂移** —— `<a>` 分支的词表漏了 `link`（非 `<a>` 分支里有），
     所以 `<a class="el-link">删除</a>` 反而放行；
  2. 中文后台"操作列"的类名（`opt-col` / `operate` / `caozuo` / `cell-ops` / `handle` / `edit`）与
     `style="cursor:pointer"`、`href="javascript:…"` 完全没有判据；
  3. `triggerOk` 只看右邻格的**文字**，没先判"右邻格本身就是控件"。
- **加固（两个方向都要对）**：
  1. `<a>` 与非 `<a>` 共用同一套类名判据；
  2. 新增操作列弱信号（类名表 + `cursor:pointer` + `javascript:` 伪协议；**`href="#"` 故意不算** —— SPA 里
     `#` 占位正文链接常见，宁可漏判也不丢内容）；
  3. `triggerOk` 先 `isInteractive(右邻格)`；
  4. **弱信号必须配"该元素整段文字由操作词拼成"的守卫** —— 否则
     `<div class="edit-area">南京市</div>` 这类"类名像操作列、装的却是正文"的容器会被整段删掉，
     这正是本项目最怕的**静默丢内容**。操作词表刻意**不含**「通过 / 驳回 / 启用 / 停用 / 审核 / 关闭」——
     这些在审核后台常作为**字段值**出现，误判就会丢内容。
- **结果**：控件形态泄漏 **10 → 0**（只剩"右格只有一张图"仍算内容，这是**有意保留**的：抓取值支持 `<img>` 缩略图）；
  正文误删 **0 / 6**。
- **影响面**：放宽只作用于 `features/fetch.js` 内部（`cellText` / `cellVisualText` / `triggerOk`），
  组合词读的是原生 `textContent` —— **高亮与组合词完全不受影响**（已逐处核对调用点）。
- **回归网**：`meta-check` 新增 1 条红线（4 个判据缺一不可）；单测新增 **26 条**
  （18 种"只有控件"形态 / 5 种"类名像操作列但装正文"的反向守卫 / 混排 / 右邻格本身是控件 / 只有图片）；
  真浏览器装置新增 3 行控件行并断言不进面板。

### K9 · 抓取表格「首行被当成表头」整行刷底色 —— **已修复（用户截图指出）**
- **现象**（用户原话）："为什么每列第一个单元格都标了底色。要么只有作为列标题的 `审测一体审核结果描述` 标颜色，
  要么就都不标啊。因为后面的内容对于整体来说都是 `审测一体审核结果描述` 后面的内容，而不是行标题。"
- **根因**：`content.css` 有一条 `.kh-table tr:first-child td { background: var(--kh-brand-soft); … }`。
  它对 **Markdown / 富文本表格**是对的（那类表第一行确实是表头），但抓取表格的第一行是**数据**
  （`[字段 label][二级标题/分组标题][内容]`），于是「基本信息 / 驳回字段：主标题 / 32位包:」被一起刷上底色 ——
  看上去像"每列的行标题"。
- **修复**：
  1. `fetch.js` 给抓取表格打 `kh-table-fetch` 标记类，字段 label 格打 `kh-table-label`；
  2. 着色规则收窄为 `.kh-table:not(.kh-table-fetch) tr:first-child td`（只对真表头生效），
     另加 `.kh-table .kh-table-label`（**只有字段 label 格上色**，它才是左列的列标题）；
     面板（`important-note.js`）与备注卡片 / tooltip（`note-card.js`）的 shadow 样式同步；
  3. `important-note.js` 摘取可信表格的正则放宽为 `kh-table(?: kh-table-fetch)?`，旧内容也照旧能挂载。
- **回归网**：
  - `meta-check` 新增 2 条红线：抓取表格必须带 `kh-table-fetch` / `kh-table-label` 标记；
    `content.css` 不得出现无差别的 `.kh-table tr:first-child td`（判据带 `(?![\w:.-])`，避免误伤 `:not(...)`）；
  - 单测：只有字段 label 格带 `kh-table-label`，分组标题 / 二级标题 / 内容一律不带；
  - 真浏览器：新增断言逐个读 `getComputedStyle(td).backgroundColor` ——
    **除字段 label 格外任何格子都不许上色**，且首行非 label 的格子必须无色（实测 8 格中仅 2 个字段 label 上色）。

### K8 · 抓取多行表格「理由被挤到最右侧独立一列」 —— **已修复（用户截图指出）**
- **现象**（用户真机截图 + 圈注）：`驳回字段：X` 在中间一列，它下面的**理由**却落在最右侧另一列，
  中间留着一块空白；用户原话「为什么单独放在一列，不应该填在前面空白的部分么」
- **量到的几何（修复前）**：版本 A `基本信息 [318→458]` / `驳回字段 [458→702]` / **理由 `[702→921]`**；
  版本 B `基本信息 [199→284]` / `驳回字段 [284→758]` / **理由 `[758→921]`** —— 理由确实各占一列
- **根因（列模型自相矛盾）**：渲染时**每一行都补了一个空 label 格**，同时二级标题又用 `rowspan` 占住第 2 列。
  于是续行的格子被整体右移一列：`[空 label][空][内容]` → 内容落到第 3 列，而有标题的首行内容在第 2 列，
  同一字段的理由被拆到两列。
- **修复**：回到旧版 1.52.0 `_rowsToTableMulti` 的干净三列网格 ——
  label 只在首行出现一次（`rowspan` = 块总行数）、续行**只写内容格**（第 1/2 列已被 label 与二级标题的
  `rowspan` 占住，内容自然落回内容列）、一级分组标题 `colspan=2` 跨满 label 之外的整行。
- **回归网**：
  - 单测新增**网格展开断言** `gridOf()`：把 `rowspan/colspan` 还原成真正的网格，
    逐行断言"展开后必须 3 列"且"理由单元格与「驳回字段」单元格同在第 2 列"；
    原先的判据"每行 td 个数一致"是**错的**（`rowspan` 的行本来就不该有自己的 td），已删除；
  - `_e2e/fetch-format-select.js` 用用户两个真实样例量几何 + 出图，可一键复现修复前后对比。

### K7 · 全词 + 正则多分支：首个分支之后的词全漏 —— **已修复，根因是我自己引入的回归**
- **现象**：关键词 `BUG|FEATURE`（区分大小写 + 全词 + 正则），文本
  `xBUGy aaa xFEATUREy bbb BUG ccc FEATURE ddd` → 只命中 `BUG@24`，`FEATURE@32` 漏掉
- **定位过程**：
  1. 同一正则串在同一浏览器手工 `exec` → `["BUG@24","FEATURE@32"]`，说明**正则本身正确**；
  2. 建 `_e2e/diag8.js` 逐条打印 `exec` 结果与跨节点守卫判定 → 两条都通过守卫，说明**不是守卫挡的**；
  3. 在 Node 垫片里把同一条规则跑完整管线，打印编译结果 → **`flags=u`，没有 `g`**；
  4. 真相：`while ((m = re.exec(text)) !== null)` 靠 `lastIndex` 推进，
     **缺 `g` 时 `exec` 每次都返回同一个首个匹配** → 只会拿到第一个词（严重时死循环）
- **根因**：我在「修全词边界」时，为了躲"带 `g` 的正则对象有 `lastIndex` 状态、
  多次 `.test()` 会假阴性"，把 `buildPattern` 的 `g` 去掉了 —— 那次判断是错的：
  `g` 是"逐条产出全部命中"的**语义要求**，而状态污染的正确解法是
  **调用方复制一份再遍历**（扫描侧与组合词侧本来就是这么写的）。
- **修复（三层，防复发）**：
  1. `compiler.buildPattern` 恢复 `let jsFlags = 'g'`（含注释说明血泪教训）；
  2. `scanner` 的 `node-regex` Probe 与 `combo.matchIn` 对 flags 做 **`g` 兜底**
     （这个循环的正确性完全押在 `g` 上，不能只信任上游）；
  3. 删掉 `if (!re.global) break;` —— 它会把"缺 `g`"从死循环变成**静默只命中第一个**，更难发现。
- **回归网**：
  - `meta-check` 新增 3 条红线：`buildPattern` 初始 flags 必须含 `g`、
    多命中遍历点必须有 `g` 兜底、不得出现 `!re.global` 早退；
  - `tests/specs/compiler.test.js` 新增 `★ 多命中` 用例（**已实测：去掉 `g` 时该用例变红**）。

### K1 · 抓取块把标签所在的表头行也采集了 —— 已修复

## K53 · 图片文字识别（v1.99.99.20）

**需求**：表格里的「值」经常是一张截图（供应商 / 金额 / 结论），文字不在网页里，纯文本匹配永远命中不了。

图里出现核心词就算一次**图片命中**；结果只进面板的「🖼 图片命中」独立分区，**不产生文字高亮**、不改文本命中口径。

> **⚠️ 本段口径已作废（2026-09 起；K71 的前身 .41 改的）**：图片识别已改为**「抓取后续字段」的一个分支** ——
> 取图范围 = `KH.Fetch.cellsForHit` 给出的**配置字段值格里的全部图片**（与"字段有没有 `#图`"无关），
> 匹配用**「图片命中关键词」**（正则、不区分大小写、不要求整词，**不**回落核心词），**普通词也能用**（不再限组合词）。
> 上文"给组合词加 / 识别标题词定位到的那一格"是 v1.99.99.20 当时的口径。现行口径见文末「K62–K71」一节。

## K54 · 变更相关性预筛（v1.99.99.21）：无关变动不重建、抓取字段变化只刷面板

**病根**：`MutationObserver` 观察的是 `childList + characterData + subtree`，**任何**变动都会在 1s 静默 + 2s 限频后
触发一次**整页**重建（Clear → Scan → Resolve → Index → Render → Consume）。重页面实测：
2000 行 / 12007 文本节点 / 4334 命中时，scan ≈ 707ms、整条 rebuild ≈ 1471ms —— 页面上无关键个不停时，插件每 2 秒白跑 1.5 秒。
另外那条"内容指纹轮询"（默认每秒）**实现上一直在跑**，任何文本变化都会在 1 秒内触发整页重建，把预筛整个盖过去。

**做法**：新增 `src/core/relevance.js`，每次变更先判一次，给三种结论：
`full`（整页重建）/ `consume`（只重跑 ⑦Consume：抓取 + 面板重绘）/ `skip`（什么都不做）。
判据**只许放宽**：拿不到字面前缀的规则（罕见字逐字判定、顶层含 `|` 的多分支正则）一律按"可能有"处理；
判据本身出错也回退 `full` —— **判多只是多算一次，判漏才是事故**。

### 判据（每条都有对应用例）

| 变更 | 结论 | 为什么 |
| --- | --- | --- |
| 命中节点文本被原地改写 | full | 旧 Range 的偏移会指到**新文本的同一段** |
| 命中节点被移出文档 | full | Range 已失效（翻页整表替换走这条） |
| 新增/变更文本含任一规则前缀 | full | 可能产生新命中 |
| 变化文本**所在格子**的整段文本含前缀 | full | 跨节点命中的词被拆开、值慢慢填时，变化的那一段不含完整前缀 |
| 新进来的 `<img>` + 有**开了「识别图片文字」的规则** | full | 图片识别要重新采集 |
| 我们的高亮组已不在 `CSS.highlights` 里 | full | 页面调过 `clear()`，借这次变动自愈 |
| 命中所在表格/假表格里、不含前缀的字段变化 | consume | 命中集没变，只有抓取值变了 |
| 其余 | skip | 与命中、抓取、图片都不相关 |

### 本轮踩到并已钉住的 5 个坑（都加了回归）

1. **指纹轮询一直在跑**（默认每秒）：任何文本变化 1 秒内触发整页重建 → 预筛失效。已按注释原意收口：**有观察器时不启动**。
2. **抑制窗口内直接 `return` 会丢 `MutationRecord`**（浏览器只投递一次）→ "页面刚加载完就填入的内容"偶尔永远不高亮；以前是坑 1 那条轮询碰巧兜住的。现在改成攒起来、窗口过后统一判。
3. **`unfilterable` 把"规则没有 labelPattern"当成"无法预筛"** → 普通词会让任何文本变化都判 full，预筛完全失效。正确口径：只检查**存在**的模式；两个都不存在（罕见字）才算无法预筛。
4. **判"变更是否落在命中表格里"不能用 `rec.target`**（常是 body/大容器）→ 往 body 追加任何东西都被当成抓取相关。只收增删的节点本身。
5. **上下文取太宽造成假阳性**（两次）：① 非表格场景退化成 `el.parentElement` → 父容器是 body，整页文本必然含前缀；② 把块级兄弟（隔壁那张表）也拼进来。最终口径：表格里用格子、非表格只跟**行内**兄弟拼（与内核 `buildInlineRuns` 同一口径）。

另外**门禁自己抓到一条**：`7g` 的「`CSS.highlights.clear()` 后自愈」变红（实际 0）—— 外部清高亮不产生 mutation，
预筛又把随后的无关变动判成 skip → 高亮永远回不来。修法即上表第 6 行（健康检查）。

### 验证

- 单测 **269 通过 0 失败**（新增 `tests/specs/relevance.test.js` 9 条判据用例）
- 真浏览器 **101 通过 0 失败**（内容层 62 + UI 层 39），新增一组 4 条：
  ① 无关变动不重渲染 ② 抓取字段变化 → 面板跟着刷且高亮不重渲染 ③ 新增文本里的关键词**真的被高亮**
  ④ 拆词慢填后半截进来后**真的被高亮**
- 取证探针 `_e2e/probe-relevance.js`（12 项，含翻页只有字段变、假表格、慢填/拆词）；实测仅消费 **1–2ms**
  ⚠️ 经验：**别拿"高亮对象身份变了"当"发生了重建"的判据** —— Renderer 对"范围完全相同的组"会跳过重建，
  身份不是可靠信号；要断言的是**结果**（新词有没有高亮、面板有没有刷新）。

### 已知仍未覆盖（既有行为，非本轮引入）

属性变化完全不在观察范围（`attributes:false`：折叠展开 / `class`/`hidden` 让内容变可见）、`<img>` 的 `src` 被换掉、
跨 iframe 的变化、el-table 两表不在同一父容器的极端结构。要覆盖它们得打开属性观察并另写判据（见 `_checkpoint.md`）。

## K55 · 属性观察（v1.99.99.22）：显隐变化后必须补上高亮

**病根**：折叠展开 / 抽屉拉开 / Tab 切换 / `hidden` 去掉 / 换图，都是**属性变化** —— 不产生 childList 或 characterData，
于是内容露出来了却一直不亮（要等页面上发生别的变动才补）。

**做法**：`_observerOptions` 打开 `attributes:true` + `attributeFilter:['class','style','hidden','src','srcset']`
（浏览器侧过滤，其余属性连回调都没有）；判据见 `relevance.js` 的「②b 属性变化」分支：
- `src/srcset` → 有**开了「识别图片文字」的规则**（`meta.imgOcr`，.41 起普通词/组合词都算）则 `full`（要重采），否则 `consume`（抓取/面板里的图要刷新）；
- `class/style/hidden` → **现在可见且子树里含任一规则前缀** ⇒ `full`；**变成不可见且里面有命中** ⇒ `full`（把命中收掉）；其余 `skip`。

**用例（`content.test.js`）**：藏 → 只改 `style` 显出来（必须出现高亮）→ 再藏起来（命中必须被收掉）→ **删掉 `style` 属性**（同样必须重建）。
**反向验证**：把 `_observerOptions.attributes` 关掉 → 该用例**立刻变红**（17.6s 超时）⇒ 它确实在测属性观察。

### 本轮为此修掉的 4 个真 bug（全是自己引入的，都留了证据）

1. **`observe()` 死配置（幽灵红的根因）**：关属性观察时只改 `attributes:false`，却把 `attributeFilter` 留着 →
   这个组合让 **`observe()` 直接抛错** → 异常冒出 `setupObserver` → **boot 中断** → 该页**完全没有变更检测**
   （现象：`observerFire:0` / `queued:0` / 连 boot 首扫计数都是 0，而手动 `KH.rebuild()` 一切正常）。
   现在两个选项同进同退，且 `observe()` 失败写 `_observeError` + 打控制台错误，**不再静默**。
2. **裁决饥饿**：每批变更都 `clearTimeout` 重排计时器 → 只要还有记录持续到来，`_drainMutations` **永远轮不到**
   （`_drainCount` 不增长 = 属性变化永远不判）。改为 `_scheduleDrain`：**已排就不再排**，保证第一次变动后必定裁决一次。
3. **`MutationRecord.type` 拼错**：实际值是 **`'attributes'`（复数）**，代码写成 `'attribute'` → 属性记录永不匹配；
   单测当时用了同一个错字符串所以没抓到（已把真值提成单测常量 `ATTR`）。
4. **📋 复制按钮漏 `row.appendChild(meta)`**：面板卡片行没有 tag/文本 → K53 那组 e2e 等待条件永不成立（91s 超时）。

### 长期防护

- **`observe()` 失败绝不静默**（`_observeError` + console.error）——这类"看起来正常却一条记录都不收"的幽灵不会再出现；
- **观察目标看门狗** `ensureObserverTarget()`：`document.body` 被页面/框架换掉后观察器会盯着脱离文档的旧节点（回调永不触发），
  现在每 2 秒校验一次并自动重挂；
- **🔬 诊断资产**：`KH.Scheduler._observerFireCount / _drainCount / _observerRearmCount / _observeError`、
  `_e2e/probe-reveal.js`（藏/显/藏/删四阶段 + 判据与计数）、`_e2e/probe-ocr9.js`、以及 K53 那条 e2e 的**超时自动现场取证**。

## K56 · 裁决饥饿·第二轮（v1.99.99.25）：翻页后内容变了却一直不重建

**用户现场**：审核列表里点「提交」（提交后框架重渲染那一行）→ 审核状态那格内容已经不匹配了、**高亮却没了**，
面板里的抓取字段也不更新；**刷新有时什么都没有，切走标签页再切回来**高亮和备注又回来了。

**为什么"切走再切回"能好**：标签页重新可见走的是**另一条通道**（`request('visibility',{gap:0})` → 立刻整页重建）。
能好，就说明管线本身没坏 —— 坏的是"什么时候重建"这个决策。

**病根（K55 第 2 条的**同一个类**，第一轮的修法不够）**：`_drainMutations` 是静默窗口的裁决者，它有两条"没人管"的路：
1. **还没安静就 `return`** —— 设计上指望"下一条记录到来时顺手再排一次"。可**最后一批变动之后不会再有记录**，
   于是这一批记录永远躺在 `_pendingRecords` 里（新内容露出来了、却永远轮不到判）。
   *K55 那次只把"重置计时器"改成"已排就不再排"，恰好放大了这一条：排一次之后如果早退，就再也没人排了。*
2. **页面上有源源不断的无关变动**（计时器刷状态点、轮播改 `style`/`class`）→ `_lastMutationAt` 被一直刷新 →
   每次裁决都判"还没安静" → 顺延到天荒地老。

**做法**：
- 早退时**按剩下的静默时间自己补排**一次（`_scheduleDrain(Math.max(20, silentMs - waited))`）；
- 给静默窗口加**延迟上限 `_DEFER_CAP_MS = 3000`**：一批记录的"最早攒到时刻"记在 `_drainFirstPendingAt`，
  拖够 3 秒就**不等安静直接判一次**（判错最多多重建一次，判漏才是事故）；
- 上限只许跳过"等安静"，**绝不跳过相关性判定**（判 `skip` 照样什么都不做）；
- 新增诊断字段 `_deferCappedCount`，随 🩺 诊断一起给出（回调次数 / 裁决次数 / 拖过上限次数）。

**证据（真浏览器，`_e2e/probe-defer.js`）**：把命中格 `textContent` 整个换掉（旧命中节点脱离文档），
再每 200ms 制造一次无关变动、静默窗口设 1s：

| 版本 | 结果 |
| --- | --- |
| 旧行为 | `swap@1761 rebuilds=[] now=10845` → **9 秒零重建**、命中 0（复现用户现场） |
| 修复后 | `swap@1819 rebuilds=[2763] now=2769` → **951ms 后高亮自己回来** |

**回归（单测，`tests/specs/scheduler-defer.test.js`，5 条）**：早退必须补排 / 拖过上限必须裁决 /
正常安静路径不被上限改掉 / **上限不许跳过判据**（判 skip 不重建）/ 同一批追加不刷新计时起点。
**反向验证**：把这两处改回旧写法 → 单测 2 条**当场变红**（`exit=1`），真浏览器探针同时复现"9 秒零重建"。

**教训（值得记住）**：K55 的修法（"已排就不再排"）看起来对，但它依赖"总会有下一条记录来再排一次" ——
**凡是以"将来还会有人调用我"为前提的兜底，都是不成立的兜底**。要么自己补排，要么有硬上限。

## K57 · 「为什么一个都没命中」自查（v1.99.99.26）

**触发它的现场**：用户在内部管理页上点 🩺 诊断，拿到的是

```
状态: booted=true 本站生效=true 规则=100 命中=0 高亮组=0
整页重建: 34 次（其中变更通道 25 次），最近来源=boot
仅消费: 0 次，最近一次变更判定=skip（6 条记录）
调度: 观察器回调=3597 次，裁决=104 次，其中"拖过上限直接判"=4 次
```

注意最后一行：**回调在涨、裁决也在涨**（K56 的饥饿已经不复现了），重建也发生了 34 次 ——
但 `命中=0`。**没有命中，就没有高亮、也没有面板**，所以"看不见高亮"是必然结果；
真正要回答的是"**为什么 0 命中**"。而这个问题有三种完全不同的成因（修法互不相同）：

| 成因 | 现象 | 性质 |
| --- | --- | --- |
| ① 词在**可见文本**里却没命中 | innerText 有、命中 0 | **真问题**（匹配口径 / 组合词定位 / 跨节点） |
| ② 词只在**不可见**内容里 | textContent 有、innerText 无 | **正常**：扫描按可见性剪枝，显出来就会补上 |
| ③ 词不在**这一层文档**里 | 两个口径都没有 | 内容在 iframe / 图片 / 画布 / 影子根 / 还没渲染 |

**做法（只读、按需）**：

## K59 · 命中明细 + 组合词「未命中现场」（v1.99.99.29）

**为什么加**：用户说"某个格子该亮却不亮"，而诊断只给出「命中=1」——既不知道是哪条规则命中的，也不知道他要的那条规则到底命中没有。于是加两段：

## K60 · 「内容凭空显出来」的三条兜底（v1.99.99.30）——「提交后不高亮、刷新才好」的正解

**决定性证据**（用户贴回的 K59 诊断，提交后 vs 刷新后）：

| | 提交后（坏） | 刷新后（好） |
| --- | --- | --- |
| 命中 / 高亮组 | **0 / 0** | 4 / 1 |
| 上一轮扫描 | **文本节点=29**，命中=0（10ms） | 文本节点=463，命中=4（95ms） |
| 同一时刻文档 | 文本 4426 字 / **文本节点 512** | 文本 4426 字 / 文本节点 512 |

`上一轮扫描: 文本节点=29` 而文档里有 512 个文本节点 ⇒ **那次重建发生在内容出现之前，之后再也没有重建**。
匹配、定位、登记、渲染都已证明与 .17 等价（见上面的 bisect 表），所以问题只能是"**这一轮到底扫没扫**"。

**为什么之后没有重建**：这类框架用 **CSS 动画/过渡**把详情区显出来 ——
动画只改样式计算结果，**DOM 一个节点、一个属性都没动** → 「childList / characterData / 属性白名单」三种观察全都收不到记录。
旧版（v1.99.99.17）能工作，正是因为它那条**每秒文本指纹轮询**还在跑（P1 在 v1.99.99.21 把它收口掉了 ——
当时它确实是"每秒白跑一次"的元凶，但它同时也是这种情况唯一的救命绳）。

**做法（三条互不干扰的兜底，都只读/限频，不会变成"每帧重建"）**：

| 兜底 | 触发条件 | 覆盖的现场 |
| --- | --- | --- |
| `setupAnimWatcher`（`animationend`/`transitionend`，捕获阶段） | 页面上任何动画/过渡**结束** | 内容由 CSS 动画/过渡显出来（本轮 e2e 复现并反向验证的就是这条） |
| `setupGrowthWatcher`（默认每 1s） | 正文文本总量**显著变长**（`growthVerdict`：≥ max(300 字, 15%)） | 内容在观察器换 body/重挂的空隙里长出来、记录丢失 |
| 保守档指纹轮询（`setupFingerprintWatcher`） | 仅在 `changeHandling:'always'` 时恢复旧版每秒全文指纹 | 用户主动选择"旧行为"时，把 .17 那套兜底整套还给他（**v1.99.99.31 已按实测去掉，见 K61**） |

**诊断加强**：「上一轮扫描」那行现在带 **距现在多少秒** + 未收进文本节点的**按原因分类**（不可见子树 / script·style / 可编辑区 / 插件自身 UI / 空文本 / 无父节点），
并新增两个兜底计数（`animFallback` / `growthFallback`）。以前只有一个"不可见剪枝"，而且它数的是**元素** —— 一个不可见祖先能吃掉几百个文本节点，所以"扫描 29 / 文档 512"在旧报告里看不出所以然。

**回归**：
- 真浏览器新组「内容由 CSS 动画显出来（K60）」：藏在 `visibility:hidden` + 动画里 → **动画前连查两次确认 0 命中**（证明这段时间没有别的通道在救）→ 动画结束（无任何 DOM 变动）后必须补上高亮。
  为隔离这条通道，本组把"文本量暴涨"的间隔调到 60s。
- 单测 `tests/specs/scheduler-fallback.test.js` 3 条：`growthVerdict` 判据（29→4426 判重建；时钟改写不判；内容变少不判；小页面多 100 字不判）、`_fire` 必须记下本轮文本总量、涨势检查只在"页面变动观察"开着时才挂。

**反向验证**：把 `setupAnimWatcher` 的两行监听停用 → 真浏览器该组**立刻变红**（13.4s 等不到高亮）；恢复后 ✓（5.3s），并逐字节核对 sha256。
**踩坑留档**：第一次反向验证**通过了**（假绿 8.3s）—— 原因是"迟到的 config 重建"恰好发生在动画之后、把用例救了过去。
修法：用例在注入装置前先等 1.5s 让配置热更新落定，动画延迟拉到 2.5s，并在动画前**连查两次** 0 命中。**反向验证必须证明"没有它就不行"，不能只看"有它就过"。**

## K61 · 智能档 vs 保守档的消耗实测 + 去掉保守档那条冗余指纹（v1.99.99.31）

**编辑器模块化（.42 K70 / .43 K71）**

- **.42（K70）**：单元格组合 / 重要笔记那两颗胶囊从模块**左侧**挪到**标题行右侧**，文案统一为「启用」（原「启用组合」/「重要」）；OCR 三件控件从「单元格组合」搬到「抓取后续字段」（它本来就依赖抓取字段）。副作用是弹窗**反而矮了 32px**（实测 597 → 565px）。
- **.43（K71）**：「抓取后续字段」新增第 4 颗「启用」胶囊（新落库键 `fetchEnabled`，缺键按非空 `fetchLabels` 反推、显式 `false` 绝不翻回）；**口径 A 各管各的** —— 每颗胶囊只开关自己模块的字段，未勾选 → 置灰不可操作、**内容保留**；未启用时编译层把 `meta.fetchLabels` 归一成空串（**编译层是唯一漏斗**，下游零改动）⇒ 面板里真的不出现抓取值；「重要笔记」未勾选则**该词自己的笔记正文**不进面板（`important || wantFetch` 决定卡片在不在，正文按模块归属）；「组合方向 = 上下」时「取值格（右起）」**禁用 + 一行说明**（值保留）；文案全面清理（模块标题不在正文重复、长解释进 tooltip、四条说明 ≤18 字）。
- **已知且有意（K71 裁定）**：`fetchEnabled` 是**唯一不进 CSV 的模块开关**（CSV 仍 18 列）⇒ CSV 往返后按非空「字段」反推＝**启用**；**要连开关一起带走请用 JSON 导出**。

**K74 · 嵌套表格的「抓取范围」（测试版 2.0.0.1）**

- **症状（用户报）**：命中在**嵌套表格的内层**时抓取完全不生效（`fetch.js` 只取 `nearestTable` ＝最内层）⇒ 面板分成两张卡，内层那张**没有任何抓取值**。
- **新落库键 `fetchScope`**（`csv: 0`，仍是 18 列）：`auto`（默认，**就近优先只用一层**）/ `self`（只本层＝老行为）/ `outer1`（只紧邻外层）/ `outermost`（只最外层）/ `all`（内外都抓、各层合并）。界面文案「抓取范围」，未启用抓取模块时禁用；归一函数 `Config.normalizeFetchScope` 读/写/消费**三处共用同一个**（缺键/非法 → `auto`，显式 `self` 绝不翻回）。
- **行级口径统一（用户拍板）**：**所有层**都"**命中所在那一行优先，找不到再整表找第一个**" —— 顺带修掉"每行重复 `标签|值` 的键值表抓到别的行"；标签写在表头行/单独一行这类形状（`fixtures/deep.html` Z 组）行为不变（整表兜底）。
- **图片识别同源**：`img-ocr.js` 传同一个 scope ⇒ 你选哪一层抓字段，就从哪一层的值格取图；`all` ＝各层值格的图并集（沿用按 URL 去重）。
- **面板分卡规则未动**：同一外层行的内外两处命中得到同一份正文 ⇒ 按既有"内容一致才同卡"**自然合并成一张卡**；选 `outer1`/`outermost` 且内外都有字段时内容不同 ⇒ 分成两张（正是用户要的"做区分"）。
- **性能（§四.8 硬约束）**：`blockFor` 的缓存键从 `(root, labels)` 扩成 **`(root, 行号, labels, scope)`**（方案 a）——"行级优先"让同一张表的不同行可能给出不同结果，旧键会串味。整表兜底按 `(层表格, scope, label)` 再缓存一层 ⇒ 额外开销只是"每行一次行内扫描"，800 行 / 3000 行重页面预算用例仍绿。
- **装置**：`_e2e/fixtures/nested-hit.html`（A 表内外都命中 / B 表只有内层命中）+ `_e2e/probe-nested-hit.js`（取证）；内容层新增一组、单测新增 `tests/specs/k74-nested-fetch-scope.test.js`。
- **组合词的定位一行未动**（`combo.js` / `cells.js` 未改）；假表格路径未动；CSV 仍 18 列。

**K75 · 假表格不越界 + 图片识别以"真命中"为前提 + 抓取模块默认关（测试版 2.0.0.2）**

- **假表格不再越界（用户 ①）**：无 `<table>` 时原来从命中元素一路向上找"文本含全部标签的祖先"，
  **最坏接受 `body`** ⇒ 命中词出现在**正文标题/段落**里时会抓到页面任意一张表的标签，面板多出一张内容不相关的卡。
  现在作用域 = **命中所属的那个（假）行容器**（`Cells.fakeRowOf`；扁平形式 `.row > .label + .value` 取父容器），
  且要求**标签元素与命中在同一行容器**；命中不在任何行容器里（标题 / 段落 / 裸文本）⇒ 假表格路径**直接返回空**。
  真 `<table>` 路径（K74 的行级优先 + 整表兜底）**一行未改**。
- **图片识别只看真命中（用户 ③）**：删掉 `combo.js` 里两处 `pushImgAnchor`（左右格 / 上下格在**标题词定位到那一格**时就登记锚点，
  **不看核心词有没有命中**）与 `img-ocr.js` 对 `ctx.imgAnchors` 的消费；锚点现在**只来自命中所在格**
  （普通词与组合词同一套 `cellOfHit`）。**准入三条不变**、`仅抓取` 仍不 OCR、取图仍按 `fetchScope` 从「字段」值格取。
- **`fetchEnabled` 默认改关（用户 ④）**：新建关键词时该模块默认**未勾选**（与「单元格组合」「重要笔记」一致）；
  **迁移规则一个字没改**（缺键 ⇒ 按非空 `fetchLabels` 反推＝启用）⇒ **存量配置照旧抓取**。
- **口径作废登记**：「组合词勾了识别图片文字，就识别标题词定位到那一格里的图」不再适用。
  想识别"截图里的字"，正确配法是让**核心词用页面上真实存在的文本**（如同行另一列的词），
  命中后 OCR 读「字段」值格里的图，再用「图片命中关键词」判图里的字 —— **没命中就不看图片**。
- **装置/取证**：新增 `_e2e/fixtures/fake-scope.html`（标题命中 + div 假表格）、`_e2e/probe-ocr-nohit.js`（没命中的三条必须 0 条）；
  单测新增 K75 用例（假表格三态 / 锚点只来自命中 / 取图只看命中那张表）。

## K79 · 抓取层级口径重梳（测试版 2.0.0.6）
- **用户症状**：① 组合词「仅抓取」（标题词 + 核心词留空）勾了「内外都抓」仍然**抓不到内部需要的字段**；
  ② 普通词只勾「仅抓外层」却**抓到了内部相同但不需要的字段**。
- **用户口径（重梳）**：**当前层**＝命中格**直接所在**的那张表；**内层**＝当前层里**任意单元格**嵌着的表
  （不限于值格）；**外层**＝包着当前层的表；三方向可多选，**新建默认＝当前层**；**外层取值要排掉内表文字与图片**。
- **根因（症状①）**：`仅抓取` 的锚是**标题格**，旧实现只沿"祖先表"链找 ⇒ 挂在**同一层另一个单元格**里的
  内表永远看不见。**根因（症状②）**：值块把值格内嵌表的整段文字都读成了外层字段的值。
- **改法**：`config.js` 换成 `FETCH_DIRECTIONS=['self','inner','outer']` + `fetchScopeSpec()`
  （`auto` 用 `nearestOnly` 表达"就近一层"）；`fetch.js` 新增 `innerTablesOf`/`outerTablesOf`/`layersFor`，
  `resolveLayerCells` 逐方向取层并合并（同名同值去重、异值加层级后缀）；值读取加 `skipNestedTables`，
  字段的图也排除嵌表里的图（`insideNestedTable`）。
- **兼容**：旧值 `outer1`/`outermost` → `outer`（**合并成一档**，changelog 已披露）；`all` → `self+inner+outer`；
  `auto` **原样保留**；**缺键/非法 → `auto`**（＝2.0.0.1 之前那份配置的口径，不许因为默认改成当前层而少抓外层）；
  「默认＝当前层」由编辑器 `FieldMap.def` 承担（新建关键词落库即 `self`）。
- **真机取证**：`_e2e/fixtures/k79-nested-cells.html`（形状 A 内表在别的单元格 / 形状 B 内表在值格里）
  × `_e2e/probe-nested-scope.js` **13 条断言全绿**（K1 组合词只勾内层 ⇒ 拿到内表字段；K2 内外都抓两份带后缀；
  K3 旧值 auto 不含内层；K4 只勾外层不混内表文字；K5 缺省＝当前层；K6 旧值 `outer1` ≡ `outer` 逐格同值；
  K7 除"值格只有嵌表"那条外每张卡都有抓取值）。
- **反向验证 2 轮**（各只红目标族，复原后核 sha256）：① `innerTablesOf` 退回祖先链 ⇒ K79 三条红；
  ② 去掉 `skipNestedTables` 与图片排除 ⇒ 四条红（打印里能直接看到症状② 的原文混入）。
- **单测**：572（本轮 +10，新增 `tests/specs/k79-fetch-layers.test.js`；K74 两份 spec 的旧档位断言按新口径重写）。
